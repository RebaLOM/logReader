# Функциональная совместимость ядра LOGER 2.0

Инвентаризация основана на исходниках `logReader/` и `logReader.Tests/`, а не на предположениях из задания. Ядро — библиотека .NET 10 с ClosedXML 0.105.0. WinForms находится в отдельном проекте. Финальная функциональная база — **bfbea8167f63e5bfa4c4780c308caa2fe5b24697**. После первоначального редизайна перенесены все его изменения ядра относительно 6310fd5; иных изменений production-алгоритмов, настроек сборки и зависимостей ядра нет.

Изменения появились в **ee4494caa9efc9e4c784aefe8ec1d1931249f1bc** и без изменений унаследованы af256cf4 и bfbea81. Сам bfbea81 не менял ядро или его тесты. Точный patch затронул шесть файлов ядра: `DstConnectBlockTracker.cs`, `TrcBlockDetector.cs`, `ExcelLayoutBuilder.cs`, `Processing/DstConnectCsvWriter.cs`, `Processing/StepOutputWriter.cs`, `Processing/TimeSeriesOutputWriter.cs`; три файла тестов: `DstConnectBlockStateTests.cs`, `DstConnectProcessorTests.cs`, `ProcessingPipelineTests.cs`. Все **55 файлов ядра (54 .cs + .csproj)** независимо извлечены из Git bfbea81; Git blob каждого архивного и текущего файла совпал с target. При сравнении raw SHA256 архив приведён к CRLF/BOM текущего checkout без изменения Git blob.

Исторические проверки базы 6310fd5: исходный набор **120/120** в Release, 0 ошибок, 0 пропусков по runner, 4 секунды; с 13 дополнительными cases в `CompatibilityRegressionTests.cs` — **133/133**, 5 секунд; повтор после UI — **133/133**, 1 секунда. После интеграции bfbea81: **137/137**, 0 ошибок, 0 пропусков по runner, 1 секунда; это 124 cases target и все сохранённые 13 дополнительных cases. Из четырёх добавленных target cases один проверяет период ДСТ, три — CSV milliseconds/Excel. Старый gap-test изменён на сетку периода; DST time-assert теперь проверяет миллисекунды. Значение времени test runner — длительность набора, не benchmark производительности. Сырые исходный и финальный TRX, включая `test-results/after-bfbea81/after-bfbea81.trx`, команды и JSON сохранены в Git.

**Историческое ограничение счётчика PASS:** два старых теста условно возвращались без проверки, поскольку отсутствовали `Downloads/TimeFormatCSV_2121_0_20260527T114622.csv` и `Desktop/trc examples`. После предоставления `DST_LOGER` введён `LOGER_TEST_DATA_ROOT`: весь набор **137/137 PASS** с реальными проверками timestamps в 22 матричных CSV и периода в 38 TRC, без условного возврата этих двух тестов. Первые реальные timestamps сравниваются с независимым `TimeSpan.Parse`; отсутствие старого конкретного файла не выдаётся за проверку его значения 257 ms. Полная обработка реального набора: 71 PASS, девять одинаковых FAIL в bfbea81/LOGER и пять входов без подходящего описания; [real-data.md](real-data.md).

Статусы ниже относятся к ядру: `AUTO PASS` — проверка выполнена автоматическим тестом; `PERF/HASH PASS` — выполнен pipeline benchmark, стабильны число строк и SHA256 выходов; `CODE PRESERVED / NOT TESTED` — путь найден в исходниках и сохранён, но самостоятельный сценарий не проверен. Доступность через живое UI доказывается отдельным UI-аудитом, а не успешной сборкой ядра.

Историческое сравнение **до интеграции bfbea81**: `performance/baseline.json` и `performance/after.json`, **17/17 результатов совпали**, идентичны входы и исходники ядра 6310fd5. Медианы большого TRC→CSV: 238,77→214,07 мс; большого XLSX export: 1654,07→1336,71 мс. Эти данные не являются доказательством совместимости с последними исправлениями: её проверяет отдельная пара `baseline-bfbea81.json` / `after-bfbea81.json`. Исторические JSON и `comparison.md` сохранены без замены.

Финальная пара — **независимо собранный Git-архив bfbea81** и текущее интегрированное ядро: `performance/baseline-bfbea81.json` / `performance/after-bfbea81.json`. **17/17 hash и counts совпали**, входные файлы идентичны; общий raw SHA256 всех `.cs`/`.csproj` ядра с обеих сторон — `DCC9FB82C370E703291119BDD69621DA498D69CA29F530D5070EED41E97CD209`. Оба Release-прогона выполнены вне sandbox, одинаковым harness, по одному прогреву и пяти samples. Большой TRC→CSV: **178,21→182,33 мс (+2,3%)**; большой XLSX export: **1269,71→1244,70 мс (−2,0%)**. Отдельный большой parse/decode/aggregate: **237,53→257,06 мс (+8,2%)**. Исходники алгоритмов одинаковы; различия короткого замера не доказывают оптимизацию или регрессию алгоритма и не гарантируют производительность любых реальных логов.

У обоих финальных JSON `FreshOutputs=true`: опция `--fresh-outputs` удаляет только прошлые синтетические результаты внутри проверенного fixture root перед прогревом/каждым sample, защищает входы и выполняется **вне таймера**. Измеряется создание нового результата, **атомарная перезапись существующего файла здесь не измеряется**. Opt-in не меняет исторический режим по умолчанию. Три предыдущих after-прогона с reuse outputs прервались из-за File.Replace «Не удается удалить заменяемый файл»: два в sandbox, один вне него. Причина не установлена; неполные прогоны исключены из финальных JSON, код ядра не изменён. Проверки atomic replacement остаются в тестовом наборе. Сравнивать новые времена непосредственно с исторической парой нельзя из-за разной подготовки outputs. `compare.ps1` требует одинаковый FreshOutputs, считает отсутствующее старое поле false; проверены успешная финальная пара, отказ для смешанной методики и принятие исторической пары.

Managed allocations практически равны: для большого TRC→CSV **111,17 MiB** с обеих сторон; WorkingSet после него **118,33→135,66 MiB**, после большого XLSX **167,32→185,55 MiB**. WorkingSet относится ко всему процессу и зависит от предшествующих сценариев, не является удерживаемой managed памятью или доказательством многочасовой стабильности. Полные время/CPU/память/hash, sample values и ограничения — `performance/comparison-bfbea81.md` и JSON. Относительно исторического baseline изменился только DST CSV hash при тех же 500 строках — ожидаемый формат H:mm:ss.fff; дробный milliseconds axis и ширина Шаг проверяются отдельными target tests.

Байтовые SHA256 DLL разных сборок могут различаться: SDK включает Git commit в `AssemblyInformationalVersion`, а независимо собранный архив имеет другой путь сборки. Совместимость проверяется по исходникам и выходам, а не по равенству version metadata. UI-only ReadyToRun не применяется к ядру. Console benchmark проверяет processing/export и не заменяет измерения запуска и памяти UI.

## Ограничения проверки

Этот реестр не объявляет совместимость каждого click-path подтверждённой: ядро сохранено и доступные автоматические проверки проходят; реальное открытие всех dialog forms, native File/Folder pickers, open-output shell action, lock/error prompts, keyboard/focus, sorting/search и обработка больших таблиц относятся к UI-аудиту. Пока не предъявлено отдельное доказательство, эти UI-сценарии имеют статус **NOT TESTED**. Сотни/тысячи devices, все варианты malformed description data, многогигабайтные реальные логи, network shares и многочасовая стабильность также **NOT TESTED**.
