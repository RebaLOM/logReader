# Функциональная совместимость ядра LOGER 2.0

Инвентаризация основана на исходниках `logReader/` и `logReader.Tests/`, а не на предположениях из задания. Ядро — библиотека .NET 10 с ClosedXML 0.105.0. WinForms находится в отдельном проекте. При редизайне исходники, алгоритмы, настройки сборки и зависимости **ядра не изменялись**. Это дополнительно проверяет SHA256 всех его `.cs`/`.csproj` в performance harness.

До изменений UI выполнен исходный набор: **120/120** в Release, 0 ошибок, 0 пропусков по отчёту test runner, 4 секунды. После добавления 13 проверок совместимости (10 test methods, одна из них с четырьмя кодировками): **133/133**, 0 ошибок, 5 секунд. После финальной сборки UI набор повторён: **133/133**, 0 ошибок, 0 пропусков по runner, 1 секунда. Значение времени test runner — длительность набора, не benchmark производительности. TRX находятся в `docs/loger-2/test-results/` и игнорируются общим правилом репозитория; воспроизводимые команды и JSON baseline сохранены в Git.

**Ограничение счётчика PASS:** два старых теста условно возвращаются без проверки, если отсутствует внешний пользовательский файл. Здесь нет `Downloads/TimeFormatCSV_2121_0_20260527T114622.csv` и `Desktop/trc examples`. Проверка этих реальных примеров — **NOT TESTED**, хотя runner формально считает оба теста успешными. Остальные проверки и новый синтетический benchmark действительно выполняются.

Статусы ниже относятся к ядру: `AUTO PASS` — проверка выполнена автоматическим тестом; `PERF/HASH PASS` — выполнен pipeline benchmark, стабильны число строк и SHA256 выходов; `CODE PRESERVED / NOT TESTED` — путь найден в исходниках и сохранён, но самостоятельный сценарий не проверен. Доступность через живое UI доказывается отдельным UI-аудитом, а не успешной сборкой ядра.

Финальное сравнение `performance/baseline.json` и `performance/after.json`: **17/17 результатов совпали**, идентичны входные файлы и SHA256 исходников `.cs`/`.csproj` ядра. На сценарий — один прогрев и пять измерений. Медианы большого TRC→CSV: 238,77→214,07 мс; отдельного большого XLSX export: 1654,07→1336,71 мс. Все 17 медиан после ниже baseline, однако код ядра не менялся: эти различия нельзя приписывать оптимизации алгоритмов или переносить на любые пользовательские логи. Managed allocations практически равны; WorkingSet процесса колеблется между сценариями и не доказывает отсутствие многочасовых утечек. Полные время/CPU/память/hash и ограничения — `performance/comparison.md`.

Байтовые SHA256 DLL baseline и after различаются. SDK автоматически включил новый Git commit в `AssemblyInformationalVersion`; сравнение алгоритмов опирается на неизменные исходники и совпавшие выходы. Сборка ядра в опубликованном UI совпадает с обычной Release-сборкой; UI-only ReadyToRun не применяется к ядру. Этот console benchmark проверяет processing/export и не заменяет измерения запуска и памяти UI.
